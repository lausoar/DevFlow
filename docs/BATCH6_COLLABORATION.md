# 第 6 批：协作与检索

> 对应审计报告里「协作沟通」「文档知识库」两组缺口中最影响日常使用的几项：
> 消息动作（编辑/撤回/表情/已读）、通知偏好与免打扰、全文检索。

## 一、全文检索（替代 `LIKE '%kw%'`）

### 问题

全局搜索此前对五个实体都做 `LIKE '%kw%'`——前导通配符让索引完全失效，
等于每次搜索五次全表扫描。文档正文（`LONGTEXT`）根本不参与搜索。

### 方案：MySQL FULLTEXT + ngram

```sql
ALTER TABLE document ADD FULLTEXT KEY ft_document (title, content) WITH PARSER ngram;
-- task / bug / requirement / chat_message 同理
```

ngram 解析器把中文按 2 字切分建倒排索引，因此"登录失败"这类中文可以走索引。

### 实测出来的两个限制（重要）

我在真实 MySQL 8.0 上验证了这几点，都不是文档里会主动告诉你的：

1. **单字查询命中不了**。`ngram_token_size` 默认 2，`AGAINST('登')` 在 BOOLEAN MODE 下返回空。
2. **纯英文/数字词命中不了**，除非写成前缀通配 `k8s*`。

因此策略是**混合**：

```
查询词长度 < 2 或 纯英文数字  → LIKE 回落（保证这类查询仍可用）
其余                         → FULLTEXT（走索引）
检索失败（索引缺失/语法错）  → 自动回落 LIKE
```

`FullTextSearchServiceImpl` 里 `isAvailable()` 先探测索引是否存在（结果缓存），
未建索引的库（比如别人的开发环境）会自动全程走 LIKE，不会因为升级代码就搜不了。

### 影响面

`SearchServiceImpl` 五类查询全部改为「先 FULLTEXT 取 id → 再回表取实体」，
并**新增了正文检索**：文档能搜到正文，任务/Bug/需求能搜到描述。

## 二、消息动作：编辑 / 撤回 / 表情 / 已读

### 编辑与撤回

`chat_message` 增加 `edited_at / recalled_at / recalled_by / original_content`。

**撤回语义**：`content` 置为「此消息已撤回」，原文写入 `original_content`。

- 前端只需判断 `recalled_at` 是否非空；
- 审计侧仍能查到原文——这是合规要求（金融/政企常见），不能真的物理删除；
- 列表接口会再兜一层把 `originalContent` 置空，避免任何路径泄露。

约束：只能操作自己发送的消息；已撤回的消息不能再编辑。

### 表情回应

`chat_reaction`，`(message_id, user_id, emoji)` 唯一，重复点击即取消。
批量取用 `reactionsOfMessages` 一次查完，避免每条消息一次查询。

### 已读回执

`chat_read_state` 按「频道 + 用户」记录 `last_read_at`。

**为什么不是逐条已读表**：一条消息 × 一个成员 × 一次已读就是一行，
一个 50 人项目 × 每天 200 条消息 = 每天一万行，一年三百多万行，很快就会拖垮库。
按时间点记录则是「成员数」级别的行数。

两个细节：
- **只前进不后退**：乱序到达的已读请求不会把位置改小；
- 未读数 = `created_at > last_read_at AND sender_id != 自己`（自己发的消息不计未读）。

## 三、通知偏好与免打扰

`notification_preference`（按类型开关）+ `sys_user.dnd_start/dnd_end/dnd_enabled`。

**关键设计：关掉 ≠ 不产生**。关掉某类型或不推的时段里，通知**仍然入库**，只是不实时推送。
理由：静默丢弃通知比多推一条危险得多——用户永远不知道自己错过了什么。
入库后用户进通知中心仍能看到。

免打扰时段支持跨天（`start > end` 表示 22:00–08:00 这类）。

偏好查询失败时**默认推送**（fail-open），宁可多推也不静默丢。

## 四、前端

- 设置页新增「通知偏好」卡片：按类型勾选 + 免打扰时段 + 一键全开/全关；
- 聊天页新增 API 层（`chat-actions.ts`）：编辑、撤回、表情切换、已读上报、未读数查询。

> 说明：聊天 UI 的动作按钮（长按菜单、表情条）本批只做到了 API 与状态层，
> 交互细节（右键菜单、表情选择器、已读人数浮层）留待下一批——那部分主要是 UI 工作量，
> 不影响数据链路。

## 六、本批未做

- **聊天 UI 的动作交互**（右键菜单、表情选择器、已读人数浮层）：只有 API 与状态层；
- **ES / OpenSearch**：FULLTEXT 已能撑住中小规模，数据量再上一个量级才需要换引擎；
- **消息搜索**：`ft_chat_message` 索引已建，但聊天页还没做搜索框；
- **订阅制通知**（关注某工作项才收变更）：当前是"按类型"而非"按对象"。
