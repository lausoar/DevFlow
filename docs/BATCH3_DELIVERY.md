## 一、环境与部署记录

### 数据模型

```
deploy_environment（项目内环境：DEV / TEST / STAGING / PROD）
deployment（不可变部署记录）
```

`deployment` 的关键字段：版本快照（`version`，版本被删也不丢历史）、提交、状态机、
审批链（`approvedBy` / `approvedAt` / `approvalNote`）、起止时间、`rollbackOf`（回滚指向）。

### 状态机

```
PENDING_APPROVAL → APPROVED → DEPLOYING → SUCCEEDED
                        ↓                     ↓
                    CANCELLED(驳回)        ROLLED_BACK
                                DEPLOYING → FAILED
```

**为什么要一步一动作而不是直接改状态字段**：每一步都会落时间戳（审批时间、开始时间、完成时间），
DORA 的变更前置时间正是靠这些时间戳算出来的。允许直接改状态就等于放弃了度量能力。

### 产品约束

- **环境是一等对象**，不是 CI 变量；有部署记录的环境不允许删除（历史是审计证据）；
- **生产环境默认需要审批**（`type=PROD` 时 `requiresApproval` 默认 1）；
- **不能自审**：审批人不能是自己发起的部署（服务端强制）；
- **环境互斥**：同一环境不允许并发的未完成部署；
- **回滚是独立动作**：生成新记录并链接 `rollbackOf`，被回滚的那次标记为 `ROLLED_BACK`，
  历史不被篡改；受保护环境的回滚要重新走审批。

## 二、DORA 四指标

`GET /projects/{id}/dora?days=30`，只统计 **PROD 环境**的已完成部署。

| 指标 | 口径 | 缺数据时的行为 |
|------|------|----------------|
| 部署频率 | 成功部署数 / 天数，折算成"次/天"或"次/周" | 返回 0 次 |
| 变更前置时间 | 本版本首个提交时间 → 部署完成时间，取**中位数** | 返回 `null`（不是 0 小时） |
| 变更失败率 | 失败（含被回滚）/ 全部已完成部署 | 无部署时 `null` |
| 平均恢复时间 | 每次失败到其后首次成功的间隔，取中位数 | 无恢复样本时 `null` |

两个刻意的设计决定：

1. **没有生产环境时返回 `hasProdEnvironment: false` + 说明文字**，而不是返回一排 0。
   一排 0 会让人误以为"部署得很少"，实际是"根本没配生产环境"。
2. **样本少于 5 次时附上"仅供参考"提示**。DORA 指标在小样本下波动极大，
   不加提示的话会变成误导性的考核数字。

用中位数而非平均值，是因为交付周期是长尾分布——一次拖了两个月的部署会把平均值拉到毫无意义。

## 三、UI 走查

`design_walkthrough` + `design_walkthrough_item`，走查项四态（PENDING / PASS / FAIL / NA）。

- **锁定设计稿版本**：建单时记录 `design_version`（未指定则取该需求的主设计稿当前版本）。
  没有这个基线，"设计改了三版之后再来验收"就没有共同口径；
- **失败项一键转缺陷**，且**幂等**：已转过直接返回原缺陷 id，不会刷出一堆重复缺陷；
- 转出的缺陷描述里带设计稿版本、设计稿链接、截图、关联需求——开发不用回头问是哪一版；
- 走查单进度：已检查数 / 通过率（不适用项不计入分母）/ 已转缺陷数。

前端嵌在需求详情里：新建走查单 → 批量贴检查点 → 逐项点通过/不通过/不适用 → 失败项转缺陷。
